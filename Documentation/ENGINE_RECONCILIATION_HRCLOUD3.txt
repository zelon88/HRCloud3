--About This File--

HRCloud3 carries its own copy of the HRProprietary Engine, as every application built on the
Engine does. The Engine is maintained for every application, so a change made to this copy
is a proposal to the Engine & not a private convenience.

This file is the record of those proposals. Every change to a file the Engine distributes is
entered here in the build that makes it, with what changed, why, what it does to the
reference application & how to see that it works. Nothing is changed in the Engine that is
not entered here.

A change is written so that it could be applied to the Engine as it stands. It names no
application, asks nothing of one that the contract does not already ask, & leaves the
reference application behaving as it did.

A versioned Engine file this application changes is stamped with the version it was taken at &
ur, for un-reconciled, as v5.0.0ur. A file it carries unchanged keeps canon's stamp. The
HRProprietary conversation merges every application's copy into canon, & only canon is stamped
plainly.

The baseline is canon v5.0.1, which is the HRProprietary repository at 1f5e243 with drop-in 35
applied as its status says. Its kernel is v5.0.1, its Engine v5.0.0, with the Setup, Dependency,
Pipeline, Authentication, Email, Page & Storage Cores at v5.0.0, the Workflow & Event Cores at
v4.3.1 & the Environment Core at v4.3.3. Until v1.0.1 the baseline was 2c576bb, the v4.3.4 starter
kit, & every change HRCloud3 made to it is canon's from v5.0.0.

THE CHANGES, AS v0.9.9 & v1.0.0 ENTERED THEM. The stamps are the ones they carried then.

THE STORAGE CORE. NEW IN v1.0.0. Resources/Engine/Cores/storageCore.php, v4.3.4ur.
  What. A Core that keeps what signed in users store in libraries an administrator lists, & the only part of
  the Engine that reaches them. A library is personal, a space per account named for its random identifier,
  or shared, one tree that admins, everyone or nobody writes. Each space has its tree, a trash & an incoming
  folder. A shared library keeps its trash, its incoming folder & Authors in a folder of its own at its top,
  which no request may name in any case, named '.'.engineApplicationSlug(), so the core names no application
  & HRCloud3's is .hrcloud3. Authors records which account added each file & folder of a shared library, by
  inode, with its kind, size & time, & a trash record names the one account that added what was deleted, so
  an admin who may write it, or that account alone, deletes it forever. Names are kept exactly as written,
  checked whole with sanitizePath(), & every folder is walked a name at a time with lstat, so a link is never
  followed, listed or acted on. Nothing is ever replaced: a file is put in place with link(), & a folder with
  rename() where the name is free. Delete moves to the trash with a record, & restore, purge & empty follow.
  Downloads stream with one Range, nosniff & a sandbox policy, with output compression turned off. The quota
  & the storage reserve are held for every write here, listener or not. A sweep empties each trash after
  --Trash Lifetime-- days & takes unfinished uploads. A page asks with StorageAction & is answered one line
  of JSON under Storage. -v reports every library.
  Why. Step 3 of HRCloud3's rebuild, which Justin scoped on 11/27/2026: personal & shared libraries, a trash,
  the Engine plus a bare Files page. One place for every file, so encryption at rest is added in one place.
  Justin chose the application's name for the shared folder, & admins or authors for deleting forever, as a
  shape to mold as sharing & social features are built. Ownership of a shared file starts from Authors.
  Errors. 52000 to 52019 are proposed for it, after the Page Core's 51000 block. 52000 is raised.
  The reference application. HRConvert2 does not turn $EngineEnableStorage on & pins no Storage Core, so
  nothing changes for it. Its session sweep never reaches Libraries, which is not a session area.
  Seen working. test_storage-cli.php, new, 72 checks. test_hrcloud3-cli.php Part 9 asks every action of the
  loader through php-cgi, & a browser drives the Files page, a library everyone writes included. Each of 34
  faults planted in the core failed test_storage-cli.php, 12 of them in who added what. Of 15 planted for
  test_hrcloud3-cli.php, in the core, its hooks, the Page Core & the contract, 14 failed it. The one left
  removes the line that turns output compression off, which changes nothing a request can see, because the
  compressing buffer is let go as well.

--What The Engine Assumes About An Application--

Entered as each is met.

THE SIGN IN PAGES ARE AN INTERFACE'S, & EVERY INTERFACE OF EVERY APPLICATION CARRIES ITS OWN COPY.
Met planning the interface, after v0.9.8.
FOR THE HRPROPRIETARY CONVERSATION TO LOOK INTO, WITH THE ENGINE THIS APPLICATION HANDS BACK.
The Engine names a page, & the application's interface draws it, from engineGui.php, with $EnginePageState. That
separation is right & is to be kept. The Engine draws no page, & an interface is a folder an administrator can replace.
What no application can get from the kit is the interface half of accounts. It exists only in HRConvert2's interfaces.
  engineGui.php                 The sign in, register, confirm, recover & reset sections, drawn from $EnginePageState.
  HRC2-SignIn.js                The page's half of signing in. HRC2SignIn holds the key, trades it on the timer, keeps it
                                in the tab & stamps every request the page sends. HRC2SignInPage switches the sections.
  HRC2-SignInTimer.js           The worker the trade runs on.
  $GuiAuthText1 to 53           The strings, in every language pack.
HRConvert2 carries two copies, one in each interface, identical but for a comment in engineGui.php. HRCloud3 will
carry a third, & every application that offers accounts another.
HRC2SignIn is the client of the Authentication Core's protocol. It decides which key a tab may take up, when a key is
traded, & which requests carry one. A fault in it is a fault in signing in, & a copy in each interface of each
application is a copy that can drift from the Core it talks to. Its endpoint & its window.name prefix are written into
it, as convertCore.php & HRC2-SIGNIN:, so a copy must be edited before another application can use it.
Proposed, each keeping the Engine free of markup & strings:
  1. The protocol half becomes the Engine's. A script holding HRC2SignIn's behaviour & nothing an interface shows, with
     the endpoint & prefix handed in by the page, & the timer worker beside it. Each interface keeps engineGui.php, the
     section switching, its stylesheet & its strings, so its look & its language stay its own.
  2. The kit carries a reference interface, as it carries the Starter, holding header.php, footer.php, engineGui.php &
     an English pack with the $GuiAuthText strings, for an application to copy & restyle.
  3. The interface loader becomes Engine mechanism. HRConvert2's verifyGui(), verifyLanguage() & verifyColors(), & the
     half of buildGUI() that loads a language pack over its baseline, are no more HRConvert2's than the sign in is.
     The contract would name the files an interface must carry & the pages it draws, & the Engine would choose the
     interface, check its version exactly, fall back to the default & load the language ladder. The Engine would still
     hold no markup.
  4. An interface may inherit from a base. HRConvert2's Default & Original share every script & every language pack
     byte for byte, & differ in their style file, their stylesheet & 162 changed lines across six markup files. A
     base interface holding what they share, & an interface holding only what it changes, would keep each a folder
     that can replace anything, with nothing carried twice. A file an interface lacks would be taken from the base,
     as a string a pack lacks is taken from the baseline pack today.
Until one of these is canon, HRCloud3's interfaces carry their own copy of the interface half, taken from HRConvert2
v4.3.4's Default interface with only its names changed, & say so in each file it took.
Where it stood at v0.9.9. Proposals 3 & 4 are in this copy as the Page Core, above. HRC3-SignIn.js has the shape
proposal 1 asks for, its endpoint & prefix handed in by the page, & is still carried by the interface. Proposals
1 & 2 are left to the HRProprietary conversation.
Where it stands at v1.0.1. Proposals 3 & 4 are canon's from v5.0.0, as the Page Core. Proposals 1 & 2 are on
canon's list for a later bite, so HRC3-SignIn.js is still the interface's.

AN APPLICATION THAT DRAWS PAGES MAY SERVE NO LOCATION. Met in v0.9.9.
The warning on every page is fixed in engine.php, above. Two quieter assumptions remain, in files left plain.
-fp prints DATA Directory unchecked with a warning, & -v prints Live exposure UNVERIFIED, for an application
whose contract gives no location the served role, where Not served would be true. And every web request
makes the hosted DATA folder & its session folders, $ConvertTemp, which such an application never writes.
Proposed: say Not served, & make the hosted DATA folder only for an application that serves it.
Where it stands at v1.0.1. The fix in verifyRequiredDirs() is canon's from v5.0.0. Not served, & the hosted DATA
folder, are on canon's list for a later bite.

THE FILE LIFETIME SWEEP REACHES EVERY PLAIN FILE AT THE TOP OF A USER'S FOLDER. Met in v0.9.9.
The Engine lets a signed in user choose how long their files are kept, & the Authentication Manager removes
any plain file at the top of their folder older than that. That fits a converter's output & not a cloud's
library. HRCloud3's settings page does not offer it, so every account keeps the default, which keeps every
file. The build that adds libraries keeps them out of the sweep's reach, or proposes a sweep scoped to the
folders an application names.
Where it stands at v1.0.0. A library is never in Users, so the sweep never reaches one, & a library's trash
has a lifetime of its own. HRCloud3's contract names $EngineFileLifetimes = array(0), so the Engine offers its
users no other lifetime, & the sweep applies none.
Where it stands at v1.0.1. $EngineFileLifetimes is canon's from v5.0.0.

A RELEASE THAT ADDS A SECTION TO config.php. Met in v1.0.0.
Fixed in setupCore.php, above. HRCloud3's --Libraries-- & --Trash Lifetime-- are a section of their own.
Where it stands at v1.0.1. The fix is canon's from v5.0.0.

--File Deletion Age Threshold-- SAYS 0 KEEPS FILES FOREVER, & THE SESSION SWEEP READS 0 AS EXPIRE EVERYTHING. Met in v1.0.0.
The Engine's half of the template says 0 keeps files forever, & cleanDataLocation() says a threshold of zero
expires everything, because every session is older than nothing, & does so. test_hrcloud3-cli.php sets it to 0
to make every session expire, & checks that no library is reached. Left plain, because it is not this build's,
& reported to the HRProprietary conversation: one of the two is wrong.
Where it stands at v1.0.1. Canon decided at v5.0.0 that 0 keeps files forever, so the request sweep, a bare -c &
the Resource Manager's sweep keep every session at 0, & -c now still sweeps them all. test_hrcloud3-cli.php
sweeps with -c now, & checks that it removed sessions & reached no library.

THE DOCUMENTATION CHECKER KNOWS ONLY THE EXAMPLE'S CODE. Met in v0.9.8.
hrconvert2-doccheck.py reports 38 names in ERROR_DESCRIPTIONS.txt, labels & functions only HRConvert2's
code has, as it does from the kit's assembled Starter. The message checker already attributes each block
to the files it names & sets aside what another application raises. The documentation checker could learn
the same rule. Left to the HRProprietary conversation, which owns both checkers, & unchanged here.
Where it stands at v1.0.1. Canon's documents name the Page & Storage Cores' settings by their shared names from
v5.0.0, so none of HRCloud3's labels is in them. From the root of the v1.0.1 tree it reports the same 38 names,
all HRConvert2's, as canon reports from its Starter by design.

THE PIN BUILD EXPECTS A BOOTSTRAP SCRIPT. Met in v1.0.1.
--build --pins builds $RequiredConfigScript from Documentation/Build/<application>-setup.sh, the bootstrap script
an application ships, & reports CANNOT BUILD where there is none, which fails the check whatever every other pin
says. HRCloud3 ships none, as the kit's Starter ships none, so --build --pins exits 1 for both with every other pin
matching. HRCloud3's pins for v1.0.1 were moved until it reported nothing else. Left to the HRProprietary
conversation: a pin whose file the application does not ship could be reported apart, & leave the check passing.

A RELEASE THAT RETIRES CODE IS REFUSED WHERE IT IS UNPACKED OVER THE HOSTED LOCATION. Met in v1.0.1.
codeMissingFromTree() holds every PHP file an installation keeps in Resources & UI against the tree -fp would
install, so a drop-in of changed files is never installed in place of the whole application. It does not read
$EngineRetiredPaths. A release whose contract retires code, as v1.0.1 retires Resources/ScanCore & the kit's
HRConvert2 does from v5.0.0, is refused by -fp run from the hosted location, naming ScanCore.php as missing,
though -fp in the installation takes that folder away itself. ABOUT_MANAGED_LOCATIONS.txt says a release that
removes code on purpose installs once Application has been moved aside by hand, & that route also installs a
config.php of defaults. Unpacked into Application, followed by --config --repair & -fp, as the same document
says for a drop-in, v1.0.1 installs over v1.0.0, keeps every value an administrator set & every account, & -fp
takes Resources/ScanCore away. Seen from a v1.0.0 installation, & README.md says to upgrade that way. Proposed:
codeMissingFromTree() leaves out every path at or beneath one the running tree's contract retires, since those
are the code a release drops on purpose & says so. Left plain, because the route that keeps an administrator's
configuration works.
